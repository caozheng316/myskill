# Python 代码生成规范 (Strict Python Code Structure Guidelines)

## 0. 【重要】确认机制 (Confirmation Protocol)

### 0.1 误判检测（优先级最高）
在响应用户请求之前，**首先判断用户意图是否真的需要编写/修改 Python 代码**：

**可能的误判场景**：
- 用户只是在讨论 Python 相关话题，而非请求编写代码
- 用户在询问问题、寻求解释，而非要求实现功能
- 用户在描述已有代码，而非要求修改或创建
- 用户只是在闲聊中提到关键词，而非下达开发指令

**误判处理流程**：
1. 当判断为误判时，不要进入需求确认阶段，而是询问用户：
   > 我注意到您提到了相关关键词，但似乎并不是要编写或修改 Python 代码。请问是否不需要调用 py-coder 技能？

2. 如果用户确认是误触发：
   - 退出本 skill
   - 按正常对话继续

3. 如果用户确认确实需要写代码：
   - 进入下一阶段（需求确认）

在用户提出项目开发或代码修改需求后，**必须等待用户明确回复"开始写代码"**，才能开始编写代码。

## 1. 核心目标
生成代码需满足以下两个核心原则：
1. **高可维护性**：结构清晰，所有函数必须包含明确的功能说明文档，适配 Windows 环境。
2. **需求充分理解**：确保用户对方案满意后再动手写代码，避免返工。

---

## 2. 代码整体布局 (Structure Layout)
整个文件必须严格按照以下 6 个区域顺序排列：

1. **简易说明区 (Docstring)**：包含详细的模块级注释（见第 4 节）。
2. **模块引入区 (Imports)**：标准库 -> 第三方库 -> 本地模块。
3. **常量配置区 (Constants)**：全大写配置常量。
4. **函数区 (Functions)**：所有功能函数，必须包含函数级注释。
5. **主流程区 (Main Process)**：`def main()` 封装核心逻辑。
6. **执行区 (Execution Guard)**：`if __name__ == '__main__':` 入口保护。

---

## 3. 详细约束规则 (Detailed Rules)

### 3.1 简易说明区 & 模块引入区
- **头部注释**：必须严格按照第 4 节定义的 8 个字段编写。
- **依赖顺序**：按"标准库 -> 第三方库 -> 本地模块"顺序导入。

### 3.2 常量配置区 (全局控制台)
- **位置**：位于 Import 之后，Function 之前。
- **内容**：仅存放全大写的配置常量（如 `FILE_PATH`, `TIMEOUT`）。
- **禁止**：禁止定义会在运行时改变的全局变量，防止被调用时产生副作用。

### 3.3 函数区 (核心要求)
- **强制文档**：**每一个函数**（包括辅助的小函数）内部第一行必须包含 `""" 文档字符串 """`，简要说明该函数的作用、输入或输出。
- **纯净性**：函数尽量通过参数接收配置，避免过度依赖全局变量。

### 3.4 主流程区 (def main)
- **封装**：所有的业务流程调度、运行时变量初始化，必须封装在 `def main():` 函数内部。
- **目的**：确保脚本被 `import` 时，`main` 函数不会自动执行，从而实现安全的模块调用。

### 3.5 执行区 (入口保护)
- 必须使用 `if __name__ == '__main__':` 包裹入口。
- 仅在此区域调用 `main()`。

---

## 4. 模块级头部注释规范 (Module-Level Header Comments)
为了确保代码的可维护性和文档的完整性，**必须**严格按照以下格式编写文件顶部的 Docstring。

### 4.1 头部字段定义 (必须包含)
头部注释需包含以下 8 个部分，对于不适用（如无输入参数）的部分可填写 "无"：

1. **[功能概述]**：用一句话概括脚本的核心功能。
2. **[启动准备]**：描述运行前需满足的环境（如依赖库安装）、配置文件准备或前置操作。
3. **[输入参数]**：命令行运行时需要的参数，或 `main()` 函数中核心的配置项来源。
4. **[输出内容]**：脚本运行结束后的产物（如控制台日志、生成的文件、数据库记录）。
5. **[模块调用关系]**：说明本模块调用了项目中的哪些模块，以及被哪些模块调用（若无则填 "无"）。
6. **[使用流程]**：简要列出 1-2-3 的操作步骤。
7. **[注意事项]**：关键的 Warning 或 Tip（如 Windows 路径问题、网络超时设置）。
8. **[可调整参数]**：列出常量配置区中用户最常需要修改的变量及其含义。

## 6. 完整工作流程（包含确认机制）

当用户请求生成 Python 代码时：

1. **误判检测**：首先判断用户意图是否真的需要编写/修改代码
   - 如果是误判：询问用户确认后退出本 skill
   - 如果是真实需求：继续下一步

2. **需求理解**：分析用户的具体需求和功能要求

3. **方案输出**（不写代码）：
   - 提供产品经理视角的分析和建议
   - 或复述完整的实现流程
   - **提示用户回复"开始写代码"**

4. **等待确认**：用户回复"开始写代码"后进入下一步

5. **设计结构**：按照 6 区域布局规划代码结构

6. **编写代码**：
   - 编写完整的头部注释（8个字段）
   - 按顺序导入模块
   - 定义常量
   - 编写带文档字符串的函数
   - 封装 main() 函数
   - 添加入口保护

7. **检查规范**：确认符合所有约束规则

## 7. 注意事项

- 始终使用 UTF-8 编码
- Windows 路径使用 raw string 或正斜杠
- 函数和变量使用 snake_case 命名
- 类名使用 PascalCase 命名
- 常量使用 UPPER_SNAKE_CASE 命名
- 每个函数必须有文档字符串
- 避免使用全局可变变量
- **严格遵守确认机制，未收到"开始写代码"不写代码**
